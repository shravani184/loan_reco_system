# CONTEXT.md

**Project:** Personalized Loan Recommendation System (PLRS)
**Nature:** ML-first personalized loan recommendation system with deterministic financial validation
**Architecture version:** 2.0 (ML-first redesign — supersedes the deterministic-fusion architecture of v1.0)
**Read this file fully before writing any code. It is the authoritative description of what is being built.**

---

## 1. What this system is

A system that answers a question ordinary eligibility checkers cannot: **not "what loan do I qualify for," but "what loan is actually right for me."**

It takes a customer's financial profile, their investment portfolio (optional), their loan requirement, their declared risk appetite, and — where a returning customer exists — their interaction history, and produces a **learned, personalized recommendation**:

- Loan product and lender
- Loan amount
- Loan tenure
- EMI
- Financing strategy (borrow / liquidate investments / hybrid)
- A personalized ML suitability score
- Ranked alternatives
- Risk information
- A full decision trace

...or, when the catalogue genuinely holds nothing suitable, an explicit **`NO_SUITABLE_LOAN`** result with structured, machine-generated reasons explaining exactly why.

**A machine-learning model makes the recommendation.** Deterministic code decides what is possible, computes every rupee, and enforces policy. This is the defining difference from v1.0, where a hand-weighted utility function made the final selection and ML only supplied input signals.

---

## 2. The one principle that governs everything

> **ML decides suitability. Deterministic systems decide feasibility. Guardrails decide policy compliance. Mathematics decides financial values. XAI explains model behaviour. The LLM explains the final system decision.**

Read that as a division of authority, not a division of labour:

| Question | Who answers it | Can it be overridden? |
|---|---|---|
| Is this option possible at all? | Deterministic eligibility + feasibility rules | No — hard gate, runs before ML |
| What does it cost? (EMI, interest, repayment) | Deterministic formula | No — never predicted, never estimated |
| **Which possible option is best for this customer?** | **Primary ML recommender** | **No — not by a deterministic score** |
| Is the ML's choice permitted by policy? | Deterministic guardrails | No — a blocked pick is surfaced, not silently swapped |
| Why did the model prefer it? | XAI (SHAP over ranker features) | — |
| How do I say that to a human? | LLM | Never computes, never decides |

Every number a user sees originates from a deterministic calculation or a model output. Nothing is ever generated by the language model.

The corollary that matters most: **when the ML recommender is unavailable, the system does not pretend otherwise.** It falls back to a deterministic ranking and stamps `recommendation_source = DETERMINISTIC_FALLBACK` on the response.

## 3. Pipeline (execution order — this order is fixed)

```
Customer input
(financial profile + optional portfolio + requirement + risk appetite + optional user_id)
        |
        v
[Financial Intelligence]      deterministic
[Portfolio Intelligence]      deterministic   (zero-portfolio is a first-class path)
[Personalization Context]     deterministic   (cold-start is a first-class path)
        |
        v
[Eligibility Engine]          rule-based hard constraints, per catalogue product
        |
        v  eligible products only (ineligible retained with reason codes)
        |
[Candidate Generation Engine] deterministic enumeration + EMI math
        |                     product x amount x tenure x financing strategy
        |                     -> feasibility marking -> dominance pruning
        v  feasible, non-dominated candidate configurations
        |
[Risk Model]                  XGBoost classifier -> PD  (a FEATURE, not a decision)
        |
        v
+=======================================================================+
|  PRIMARY ML RECOMMENDER   (XGBRanker / LambdaMART)                    |
|                                                                       |
|  for each candidate:  f(customer x portfolio x requirement x          |
|                         personalization x product x candidate config) |
|                       -> raw ranker margin                            |
|                       -> calibrated suitability in [0, 1]             |
|                                                                       |
|  -> ML-ranked candidate list  (this IS the recommendation)            |
+=======================================================================+
        |
        v
[Deterministic Validation]    walk the ML ranking in order:
[Guardrail Validation]        recompute EMI, re-check limits, feasibility,
        |                     policy caps -> first candidate that PASSES and
        |                     clears the suitability threshold wins
        v
[Recommendation Orchestrator] assembles final result + alternatives +
        |                     catalogue coverage funnel + decision trace
        |                     (assembly and bookkeeping — it does not choose)
        |
        +--> [XAI]   SHAP over the recommender -> why this candidate outranked the others
        +--> [LLM]   natural-language explanation of the already-decided result
        |
        v
[FastAPI surface]  ->  [React frontend]
```

**Two things about this order are load-bearing:**

1. **Candidate generation happens before ML, not after.** The model does not pick a product and then have a deterministic optimizer choose the amount, tenure and strategy inside it. The model scores fully-specified financing configurations, so amount, tenure and strategy are *learned choices*, not post-hoc arithmetic.
2. **Validation happens after ML, not instead of it.** Deterministic code never re-ranks. It only answers pass/fail on the candidates the model has already ordered.

## 4. Module responsibilities (what each does and does NOT do)

### Financial Intelligence — deterministic, no ML
Computes: income, monthly expenses, existing EMI, disposable income, debt burden ratio, expense ratio, EMI affordability ceiling, income stability, financial health band.
Does NOT: decide eligibility, call any model, touch loan products, score candidates.

### Portfolio Intelligence — deterministic, no ML
Computes from holdings (stocks, mutual funds, FDs, bonds, cash, crypto): total portfolio value, asset allocation, liquid assets, liquidity ratio, equity exposure, debt exposure, crypto exposure, portfolio risk band, concentration risk, unrealized gain/loss.
**Must return a valid zero-portfolio result when the customer has no investments. The whole pipeline must run without a portfolio.**
Does NOT: recommend liquidation, compute EMI, call any model.

### Personalization Context — deterministic lookup, no ML
Reads the persisted personalization store (SQLite) for a known `user_id` and emits a typed block of history-derived features: prior accepted tenure band, purpose affinity, financing-strategy affinity, session count, time-decayed engagement, prior declines.
**Cold start is a first-class path, exactly like the zero portfolio.** An unknown or absent `user_id` returns a valid neutral personalization block; the pipeline runs identically.
Does NOT: score, rank, store raw PII, or make any decision. It is a feature source for the recommender — **not a second recommender.**

### Eligibility Engine — rule-based, runs BEFORE candidate generation and before ML
Answers "can this loan product be considered at all?" Hard constraints only: credit score minimum, income minimum, requested amount within product limits, purpose match, tenure within product limits.
Output per product: eligible true/false + a machine-readable rejection reason code. **Never silently drops a product** — every catalogue product appears in the output with an outcome.

### Candidate Generation Engine — deterministic enumeration + financial math, no ML
For every eligible product, enumerates the feasible configuration space: loan amounts × tenures × financing strategies (100% borrow, 80/20, 60/40, 40/60, 20/80, 100% liquidate). For each candidate computes EMI, total interest, total repayment, liquidation amount, remaining portfolio, resulting liquidity ratio, resulting debt burden, affordability headroom.

This is bounded brute-force enumeration (a few hundred candidates per request after pruning), not a solver. Describe it accurately.

EMI formula (the only correct source of EMI in this system):
```
EMI = P * r * (1+r)^n / ((1+r)^n - 1)      where r = annual_rate / 12 / 100, n = tenure in months
```
Edge case: if `r == 0`, EMI = P / n.

Candidates that exceed affordability, or require liquidating more than the portfolio holds, are **marked infeasible, never deleted**. Feasible candidates then pass through **dominance pruning**: a candidate is dropped only when another candidate for the same product and same loan amount is better or equal on *every* comparison axis (EMI, total interest, portfolio impact) and strictly better on at least one. Dominance pruning removes objectively worse options; it expresses no preference and is not ranking.

If the customer has no portfolio, only 100%-borrow strategies are generated. This must work without special-casing anywhere downstream.

Does NOT: rank by preference, apply a utility function, call any model, or select anything.

### Risk Model — XGBoost Classifier (the SECONDARY model)
Predicts borrowing/repayment risk class + default probability from financial, portfolio and requirement features.
**Its output is a feature consumed by the primary recommender, plus a user-facing risk disclosure. It is not the recommendation and it does not select or veto anything.**
Does NOT: determine eligibility, compute EMI, select a loan, block a candidate.

### Primary ML Recommender — XGBRanker / LambdaMART (the PRIMARY model)
**This is the decision-making intelligence of the system.**

Consumes one feature vector per (customer, candidate configuration) pair — customer financial features, portfolio features, personalization features, requirement features, product features, derived candidate features, and the risk model's PD — and produces a **personalized suitability score for every candidate**. Candidates are ordered by that score; the top-ranked candidate that survives deterministic validation and guardrails is the recommendation.

Trained with customer-level groups on graded relevance labels (see §6). Its raw ranker margins are passed through a **calibration transform** (§6.4) into a bounded suitability in `[0, 1]`, which is what the acceptance threshold, the API and the UI use.

Does NOT: perform eligibility checks, compute any financial figure, filter candidates, or override a guardrail. It receives only candidates that already passed eligibility and feasibility, and it never re-checks them.

### Deterministic Validation — no ML
Independently re-verifies the ML's chosen candidate before it can be recommended: recomputes EMI from the canonical formula and asserts it matches the candidate to the rupee, re-checks product amount/tenure limits, re-checks affordability, re-checks that required liquidation does not exceed available holdings.
A validation failure on the model's top pick is a **defect signal**, is logged, is recorded in the trace, and moves the walk to the next ML-ranked candidate. It never silently corrects the candidate.

### Risk-Tolerance Guardrails — rule-based policy layer, validates AFTER ML
Caps leverage by declared risk appetite (CONSERVATIVE / MODERATE / AGGRESSIVE). Caps include: max debt-burden ratio after the new EMI, max share of portfolio that may be liquidated, whether volatile assets (crypto, equity) may be liquidated at all, max loan-to-income multiple.

**Critical behaviour:** the ML recommender still scores and ranks every feasible candidate. If the top-ranked candidate violates a guardrail, it is excluded from selection but **retained in the decision trace as `ml_top_choice_blocked`**, with the violated rule named and its cap value, and the walk continues to the next ML-ranked candidate. The response then explicitly surfaces: "the model's best match for you was X, but it exceeds your conservative profile, so we recommend Y."

Guardrails never silently delete an option and never re-rank. They answer pass/fail, nothing else.

### Recommendation Orchestrator — assembly and bookkeeping, NOT a decision-maker
Runs the pipeline in the fixed order, walks the ML ranking through validation and guardrails, and assembles the `Recommendation` object: final pick, ML suitability score, recommendation status, recommendation source, structured reasons, ranked alternatives, catalogue coverage funnel, and decision trace.

**Alternatives** are the next candidates in the model's own ranking that also pass validation and guardrails — presented in ML order, each with its own suitability score, never re-sorted by cost, EMI, or any deterministic score. How many are returned is config.

**What-if scenarios** (`/scenario`) re-run this entire pipeline on the modified inputs: new financial and portfolio metrics, new candidate enumeration, fresh ML scoring, fresh validation and guardrails. A scenario result is a real recommendation with its own suitability scores and its own status — never the previous recommendation adjusted arithmetically, and never an LLM narration of a change that was not computed.

**It contains no scoring formula that can change the ML ordering.** In v1.0 this module made the decision; in v2.0 it records one. If you find yourself writing a weighted score here that reorders candidates, you have reintroduced the architecture this redesign removed.

### Diagnostic Utility Score — deterministic, advisory only
The v1.0 weighted utility function survives, renamed and demoted:

```
diagnostic_utility = w1*affordability_headroom + w2*(1 - risk_pd) + w3*cost_efficiency
                   - w4*portfolio_impact_penalty - w5*soft_constraint_violations
```

Its only permitted uses are:
1. **Deterministic fallback ranking** when the ML recommender is unavailable (and only with `recommendation_source = DETERMINISTIC_FALLBACK` stamped on the output).
2. **Diagnostics and audit** — recorded in the trace alongside the ML score so the two can be compared offline.

**It may never reorder, veto, or adjust an ML recommendation during normal operation.** It is not "the recommendation engine". Weights live in config and are version-stamped, as before.

### Catalogue Mismatch Analyzer — deterministic
When no candidate survives to become a recommendation, this module produces the structured explanation of why (§7). It reads only real eligibility reason codes, real feasibility outcomes, real guardrail violations and real ML suitability scores. **It never invents a reason.**

### XAI Layer — TreeSHAP via XGBoost
Explains **model behaviour**, primarily the recommender: which features pushed the winning candidate above the alternatives, as signed per-feature contributions, with candidate-to-candidate comparison. Also explains the risk classifier's prediction. Feature-contribution output only, no prose.

**Contributions come from XGBoost's built-in TreeSHAP** (`predict(..., pred_contribs=True)`), not from the external `shap` package. Both models are tree ensembles, so this yields exact SHAP values with zero additional serving dependency — which is why the `shap` package is a training-only extra used for offline plots. Degrades to `feature_importances_` (gain) if contribution computation fails, and flags which was used.

### LLM Layer — Generative AI
Explains **the system's decision to the user**. Receives a validated structured payload of already-computed values and converts it to natural language. Also answers follow-up and what-if questions by routing them through the trusted pipeline first.

**The LLM must never:** compute EMI or interest, determine eligibility, compute portfolio value, generate risk or suitability scores, rank or re-rank candidates, select a strategy, invent a catalogue product, override a guardrail, or state any number not present in its input payload. See the numeric-grounding guard in AGENTS.md §5.

## 5. Recommendation states, and the distinction that defines this product

### 5.1 Ineligible vs. unsuitable

These are different failures with different causes, different owners and different explanations, and the system must never conflate them.

| Case | Meaning | Decided by | Example |
|---|---|---|---|
| **Ineligible** | Fails a hard requirement | Deterministic rules | Product needs CIBIL ≥ 750, customer has 690 |
| **Infeasible** | Eligible, but no arithmetic configuration works | Deterministic math | Every EMI exceeds the affordability ceiling |
| **Guardrail-blocked** | Eligible and feasible, but policy forbids it | Deterministic policy | Requires liquidating 60% of portfolio; conservative cap is 25% |
| **Eligible but unsuitable** | Qualifies and is possible, but the model rates it a poor personal match | **ML recommender** | `eligible = true`, `suitability = 0.31` |
| **Recommended** | Eligible, feasible, permitted, and well-matched | ML + validation | `eligible = true`, `suitability = 0.89` |

"You qualify for this, but it is not right for you" is the sentence this system exists to be able to say. It is only sayable because eligibility is deterministic and suitability is learned.

### 5.2 Recommendation status (enum, never raw strings)

```
RECOMMENDED             a validated, permitted, sufficiently-suitable candidate was found
NO_ELIGIBLE_PRODUCTS    no catalogue product passed hard eligibility
NO_FEASIBLE_CANDIDATES  products were eligible, but no configuration was financially feasible
ALL_CANDIDATES_BLOCKED  feasible candidates existed, but every one violated a guardrail
NO_SUITABLE_LOAN        candidates survived to scoring, but none reached the suitability threshold
```

### 5.3 Recommendation source (separate enum, separate axis)

```
ML_RANKER               the primary ML recommender produced the ordering
DETERMINISTIC_FALLBACK  the ML recommender was unavailable; diagnostic utility produced the ordering
```

Status describes *what happened*; source describes *who decided*. They are independent fields — a `DETERMINISTIC_FALLBACK` run can still return `RECOMMENDED` or `NO_SUITABLE_LOAN`. **Never present a deterministic fallback as an ML recommendation**, in the API, in the UI, or in the LLM's prose.

## 6. The ML recommendation model

### 6.1 What it recommends

Not "is this customer approved" and not "which product ranks highest", but:

> Given this customer and this fully-specified financing configuration — product, lender, amount, tenure, strategy — how suitable is it, personally, for them, relative to every other configuration available to them right now?

### 6.2 Training target

Graded relevance labels over customer-level groups:

```
Customer A (group):
  candidate  (Product P1, 600000, 48m, 100% borrow)  -> relevance 3
  candidate  (Product P1, 600000, 60m, 80/20)        -> relevance 2
  candidate  (Product P3, 500000, 36m, 100% borrow)  -> relevance 1
  candidate  (Product P4, 800000, 84m, 60/40)        -> relevance 0
```

Labels are produced by an explicit, documented **labeling policy** in `training/labeling.py`, which combines affordability outcome, total cost, portfolio impact, risk-appetite alignment, and a **simulated repayment-stress outcome** (does the household survive a drawn income shock over the loan term without negative disposable income), plus calibrated label noise.

**These labels are synthetic. This is stated in the file, in the manifest, in the README and in the UI.** The ranker therefore partially reproduces the labeling policy. Two honest consequences follow, and both are to be reported, not hidden:

- Reported NDCG measures agreement with a synthetic policy, not with real customer outcomes.
- Agreement between the ML recommendation and the deterministic fallback is **not** validation of either. They share ancestry.

### 6.3 Features

One vector per (customer, candidate) pair, assembled in exactly one place (`app/ml/features.py`), used identically by training and serving:

- **Customer financial:** income, expenses, existing EMI, disposable income, debt burden ratio, expense ratio, EMI affordability ceiling, employment stability, age, credit score, financial health band
- **Portfolio:** portfolio value, liquid assets, liquidity ratio, equity exposure, debt exposure, crypto exposure, portfolio risk band, concentration risk, unrealized gain/loss (all valid and zeroed for the no-portfolio case)
- **Personalization:** purpose affinity, tenure-band affinity, strategy affinity, session count, time-decayed engagement, prior declines (all neutral for cold start)
- **Requirement:** loan purpose, requested amount, preferred tenure, declared risk appetite
- **Product:** loan type, lender, interest rate, min/max amount, min/max tenure, min credit score, min income, processing-fee band
- **Derived candidate:** loan amount ÷ income, EMI ÷ income, EMI ÷ disposable income, total interest, total repayment, post-loan debt burden, affordability headroom, liquidation amount, liquidation ÷ portfolio value, remaining portfolio value, post-strategy liquidity ratio, tenure delta vs. preferred, amount delta vs. requested
- **Risk signal:** PD from the risk classifier

### 6.4 Suitability calibration

An XGBRanker emits an unbounded relative margin, which cannot support an absolute acceptance threshold — and an absolute threshold is exactly what `NO_SUITABLE_LOAN` requires. So the trained ranker is paired with a **monotone calibration transform** (isotonic regression, fitted offline on held-out groups) mapping raw margin → `P(relevance ≥ 2)` → `suitability ∈ [0, 1]`.

The calibrator is fitted during training and **exported as a table of monotone knots (x, y breakpoints)** inside the recommender's artifact bundle. At inference it is applied with `numpy.interp` over those knots — so serving needs no scikit-learn, and the calibration is inspectable, diffable between versions, and trivially unit-testable. **It is a post-processing transform of the primary model's output, not a model in its own right** — it introduces no new learned decision and does not violate the two-model rule.

`SUITABILITY_ACCEPTANCE_THRESHOLD` lives in config, is version-stamped into every trace, and is the sole definition of "suitable enough to recommend".

### 6.5 Evaluation

The primary recommender is a ranker and is evaluated as one. Accuracy is not a meaningful metric for it and is not reported for it.

- **Primary recommender:** NDCG@1, NDCG@3, NDCG@5, Precision@1, Precision@3, Recall@5, MAP@5, MRR, Kendall's tau vs. label order, plus calibration quality of the suitability transform (reliability curve, Brier score against `relevance ≥ 2`)
- **Risk classifier (secondary):** ROC-AUC, PR-AUC, precision, recall, F1, Brier score, reliability curve
- **Baselines the recommender must beat, reported side by side:** random ordering, cheapest-EMI-first, and the deterministic diagnostic utility ranking. A recommender that does not beat the diagnostic utility baseline on held-out groups is reported as such — that result is published, not buried.

### 6.6 Exactly two models

`risk_model.json` (classifier, secondary) and `loan_recommender.json` + its calibration-knot and encoder files (ranker bundle, primary). The personalization layer is a feature source, not a model. The mismatch analyzer, validator, guardrails and orchestrator contain no learned components. **Do not add a third model.**

## 7. Catalogue mismatch — a core product behaviour

The system must be able to conclude that **nothing in the catalogue is right for this customer**, and it must never manufacture a recommendation to avoid saying so. Returning the least-bad product because the ranker produced a number for it is a defect.

### 7.1 Detection

`NO_SUITABLE_LOAN` is returned when candidates reached the recommender but no candidate simultaneously: (a) scored at or above `SUITABILITY_ACCEPTANCE_THRESHOLD`, (b) passed deterministic re-validation, and (c) passed guardrails. The three earlier statuses (`NO_ELIGIBLE_PRODUCTS`, `NO_FEASIBLE_CANDIDATES`, `ALL_CANDIDATES_BLOCKED`) cover the cases where the pipeline stopped before that point, so the user always learns *how far* their request got.

### 7.2 Structured reasons

Every mismatch reason is a typed code with the concrete values that triggered it, sourced from an actual rule evaluation or model output. Reasons include, non-exhaustively:

```
CREDIT_SCORE_BELOW_MINIMUM              INCOME_BELOW_MINIMUM
AMOUNT_ABOVE_PRODUCT_MAX                AMOUNT_BELOW_PRODUCT_MIN
TENURE_OUT_OF_RANGE                     PURPOSE_NOT_SUPPORTED
EMI_EXCEEDS_AFFORDABILITY               DEBT_BURDEN_CAP_EXCEEDED
LOAN_TO_INCOME_CAP_EXCEEDED             LIQUIDATION_EXCEEDS_PORTFOLIO
LIQUIDATION_SHARE_CAP_EXCEEDED          VOLATILE_ASSET_LIQUIDATION_PROHIBITED
SUITABILITY_BELOW_THRESHOLD             REQUIRED_AMOUNT_UNREACHABLE
```

Each carries the observed value, the threshold or cap it failed, and the product or candidate it came from. **No reason may be generated that does not correspond to a rule that actually fired or a score that was actually computed.** The LLM renders these reasons; it does not author them.

### 7.3 Catalogue coverage funnel

Every response — successful or not — carries a coverage funnel, so the outcome is legible rather than mysterious:

```
12  catalogue products
 4  passed eligibility
 4  produced at least one feasible candidate
86  candidates generated (after dominance pruning)
86  candidates scored by the recommender
 0  candidates at or above the suitability threshold
--------------------------------------------------
    NO_SUITABLE_LOAN
```

This is materially better than "loan not recommended", and it is the difference between a rejection and useful guidance.

## 8. Fallback behaviour

If `loan_recommender.json` or its calibration knots are missing, corrupt, or fail to load, the pipeline continues:

```
ML recommender unavailable
        -> log the failure with the artifact path and error
        -> rank candidates by diagnostic_utility_score
        -> recommendation_source = DETERMINISTIC_FALLBACK
        -> the same validation and guardrail walk runs unchanged
        -> the flag is present in the API response and visible in the UI
```

The same applies to the risk model: if it cannot load, its PD feature is imputed to the training-set median, the imputation is flagged in the trace, and the recommender still runs.

**A fallback is never silent and is never described as an ML recommendation.** In fallback mode the ML suitability field is null, not zero, and not a rescaled utility score.

## 9. Decision trace

Every recommendation carries a trace that reconstructs the whole decision:

```
customer input snapshot (non-PII)
  -> financial features
  -> portfolio features
  -> personalization features (or cold-start flag)
  -> catalogue: every product with eligibility outcome + reason code
  -> candidate generation: counts generated / infeasible / dominance-pruned
  -> risk model: class, PD, model version
  -> ML recommendation: full ranked candidate list with calibrated suitability scores
  -> validation walk, in ML rank order, per candidate:
         candidate id | suitability | validation result | guardrail result | outcome
  -> ml_top_choice_blocked (when the model's first pick failed a rule):
         candidate, suitability, the exact rule that blocked it, the cap value
  -> selected candidate + why the walk stopped there
  -> diagnostic utility score of the winner (advisory, for comparison only)
  -> catalogue coverage funnel
  -> recommendation_status, recommendation_source
  -> CONFIG_VERSION, FEATURE_VERSION, model versions, PROMPT_VERSION
```

**The ML's top choice is never hidden because it failed a deterministic rule.** Surfacing "the model's best match for you was X, blocked by rule R, so we recommend Y" is a signature behaviour of this product, not an implementation detail.

## 10. Personalization layer

A persisted store (SQLite locally; Postgres-capable) holds, per pseudonymous `user_id`: profile snapshots, derived preference aggregates, recommendation history, and accept/decline feedback events.

- It contributes **features only**, to the primary recommender.
- Cold start (unknown or absent `user_id`) is a first-class supported path returning neutral features.
- Anonymous use remains fully supported — no `user_id`, no persistence, identical pipeline.
- Only pseudonymous identifiers and derived aggregates are stored. Raw identity documents, contact details and free text are never persisted.
- A deletion path (erase all rows for a `user_id`) is part of the layer's contract, not a later addition.
- Personalization features are versioned with `FEATURE_VERSION` like all others, and a model trained without them may not be served with them.

## 11. Data

| Dataset | Purpose | Source |
|---|---|---|
| Customer financial | risk model training + features | public lending/credit data where available, else synthetic |
| Loan product catalogue | eligibility, product features, lender attributes | synthetic |
| Customer × candidate relevance | **primary recommender training** | synthetic labeling policy (§6.2) |
| Portfolio | portfolio features | synthetic |
| Interaction / personalization history | personalization features | synthetic seed data |

**All synthetic data is labeled synthetic in the file, in the model manifest, in the README and in the UI wherever surfaced.** Never present synthetic data as real banking history.

Known limitations, stated openly rather than hidden:
- The primary recommender is trained on synthetically-generated relevance labels and therefore partly learns the labeling policy that produced them.
- The risk model trained on public credit data carries genuine signal; the portfolio and personalization features attached to it do not carry learned default signal.
- Reported ranking metrics measure agreement with a synthetic policy, not real-world recommendation quality.

## 12. Training vs runtime

Models are trained **offline** and saved in XGBoost's native JSON format (`risk_model.json`, `loan_recommender.json`, plus calibration knots, encoder mappings and manifests). They are loaded once at service startup by an explicit lifespan handler and used for inference. **Models are never retrained per request, and never loaded at module import.**

Training and runtime use the **same feature-engineering code path** — one shared module imported by both, with a `FEATURE_COLUMNS` contract and a `FEATURE_VERSION` recorded in each manifest and asserted at load time. A version mismatch between a model manifest and the serving feature module is a startup failure, not a warning.

## 13. Tech stack

The dependency set is **split by runtime**, and the split is architectural rather than cosmetic — it is what keeps the deployed service inside a small memory ceiling (§17.2).

**Serving (`requirements.txt`) — everything the API imports:**

| Area | Technology |
|---|---|
| Frontend | React, TypeScript, Tailwind CSS, Axios, Recharts |
| Backend | Python, FastAPI, Pydantic, Uvicorn |
| Database | SQLite for local dev, PostgreSQL-compatible for deployment (personalization store) |
| Numerics | NumPy |
| ML inference | XGBoost (Booster loaded from JSON) |
| Calibration | NumPy `interp` over exported isotonic knots |
| XAI | XGBoost native TreeSHAP (`pred_contribs`) |
| LLM | LLM API (HTTP) |
| Version control | Git + GitHub |

**Training only (`requirements-train.txt`) — never imported by `app/`:**

| Area | Technology |
|---|---|
| Data processing | Pandas |
| Model training | XGBoost (XGBClassifier, XGBRanker), scikit-learn |
| Calibration fitting | scikit-learn isotonic regression (exported to knots) |
| Offline analysis/plots | SHAP package, Matplotlib |
| Property testing | Hypothesis |

**Pandas, scikit-learn and the `shap` package are training-time tools.** Nothing under `app/` may import them, and a test asserts this by inspecting `sys.modules` after importing the application. Models are persisted with XGBoost's native JSON format rather than pickle, so artifacts survive library upgrades and load without a pickle-compatible environment.

**No Docker.** Local runs use a virtualenv + uvicorn. Deployment targets either a managed PaaS native Python runtime (Render/Railway) with the frontend on Vercel/Netlify, or a single VM running gunicorn + uvicorn workers under systemd behind nginx. Dependencies are pinned exactly; the Python version is pinned in `runtime.txt`.

## 14. Non-negotiables

1. **The primary ML recommender chooses the recommendation.** No deterministic score may reorder or override its ranking during normal operation.
2. Exactly two ML models: the primary recommender (ranker) and the secondary risk classifier. Do not add a third. The suitability calibrator is a transform, not a model.
3. The risk model's output is a feature and a disclosure, never a decision.
4. Eligibility and feasibility are deterministic and run **before** the recommender. The recommender only ever sees eligible, feasible candidates and never re-checks them.
5. Guardrails are deterministic, run **after** the recommender, and answer pass/fail only. A guardrail-blocked ML top choice is surfaced, never silently swapped.
6. EMI, interest and every rupee figure are deterministic. Never predicted, never estimated, never produced by an LLM.
7. Loan amount, tenure and financing strategy are chosen by the recommender from a deterministically enumerated feasible set — never by a regressor, never by a solver.
8. The Recommendation Orchestrator assembles; it does not decide.
9. The system must be able to return `NO_SUITABLE_LOAN` with structured, rule-sourced reasons, and must never manufacture a recommendation to avoid it.
10. "Ineligible", "infeasible", "guardrail-blocked" and "eligible but unsuitable" are distinct, separately represented outcomes.
11. Every response carries `recommendation_status`, `recommendation_source`, a catalogue coverage funnel and a decision trace.
12. A deterministic fallback is always flagged and never presented as an ML recommendation.
13. XAI explains the model; the LLM explains the decision. They are not interchangeable.
14. The LLM never invents a number, never makes a financial decision, and never authors a mismatch reason.
15. Every user-facing number originates from a trusted calculation or model output.
16. The system must work end-to-end for a customer with no investment portfolio, and for a first-time customer with no history.
17. Training and serving share one feature-engineering path, version-checked at load.
18. Synthetic data is always labeled synthetic, and synthetic-label limitations are reported, not buried.
19. Nothing under `app/` imports pandas, scikit-learn, the `shap` package, or anything from `training/`. The serving import graph is a tested constraint, not a preference.
20. The relevance labeling policy is verified by invariant tests written before the policy itself, and is version-stamped into every dataset and model manifest.
21. The grounding guards distinguish "unverifiable" from "ungrounded", and their tolerance is never widened to make an explanation pass. A false positive is fixed in the normalizer and locked in by a corpus case.
22. Working end-to-end integration beats added complexity. Protect the demo path.

---

## 15. Scope boundary

This is a **recommendation and decision-support system**. It reads a portfolio; it never holds, controls, executes against, or liquidates assets. Any yield-offset figure is an illustrative projection, not an automated repayment mechanism. Nothing in the UI may be framed as financial advice, and an ML suitability score is a model output about product fit — never a statement about the person's creditworthiness to a third party.

---

## 16. Relationship to architecture v1.0

v1.0 built a strong deterministic pipeline in which a hand-weighted utility function selected the final recommendation and ML supplied advisory signals. That design was safe and traceable but was, accurately described, an eligibility checker with ML attached to a deterministic chooser.

v2.0 keeps every safety property — deterministic money, hard rules before ML, policy caps, full traceability, LLM confined to explanation — and moves the *choice* to a model that learns customer-to-candidate suitability. The utility function survives as a diagnostic and fallback under a name that cannot be mistaken for the primary recommender.

Nothing in this repository may describe the Recommendation Engine as the final decision-maker, or the ML layer as "one input signal among several". Those descriptions belong to v1.0 and are obsolete.

## 17. Known risks and the design decisions that de-risk them

Three parts of this architecture are materially harder than the rest and have historically been where projects of this shape fail. Each is addressed by a design decision made **before** implementation, not by care during it. These decisions are binding.

### 17.1 The labeling policy defines what the model learns (Phase 7)

**The risk.** The primary recommender's entire notion of "suitable" comes from `training/labeling.py`. A subtle flaw there — an absolute rupee threshold that misbehaves at high incomes, a stress simulation that dominates every other term, a sign error in a portfolio-impact penalty — does not announce itself. It produces a model with excellent NDCG against wrong labels. There is no downstream test that catches it, because every downstream metric is measured against those same labels.

**Resolution — five decisions:**

1. **The policy is decomposed, not monolithic.** Labels are produced in four separable stages, each independently testable: (a) a hard disqualifier mask assigning grade 0; (b) a small set of independent sub-scores, each normalized to `[0,1]` and each owning one concern (affordability, cost of credit, portfolio impact, appetite alignment); (c) a documented combination; (d) a stress-simulation demotion applied afterwards. No stage may reach into another's concern. A single 200-line scoring function is forbidden — it is precisely the shape that cannot be debugged.

2. **Grades are assigned by rank within the customer's own candidate set, not by absolute cutoffs.** A learning-to-rank model only consumes within-group order, so grading by within-group quantile removes an entire class of bugs (scale sensitivity, income-dependent threshold drift, degenerate all-one-grade groups) at no cost to what the model can learn.

3. **Invariants are written before the policy, and the policy is tested against them.** These are properties any correct labeler must satisfy regardless of its coefficients, checked with property-based generation (Hypothesis) over wide input ranges:
   - *Dominance:* a candidate dominated on every axis never outranks its dominator.
   - *Single-axis monotonicity:* holding all else fixed, a lower interest rate, lower EMI, lower total interest, or smaller liquidation share never lowers a label.
   - *Scale invariance:* multiplying income, expenses, portfolio and all rupee amounts by a constant leaves every label unchanged. This one catches absolute-threshold bugs, which are the most common and the most invisible.
   - *Appetite ordering:* a leverage-heavy candidate is never graded higher under CONSERVATIVE than under AGGRESSIVE.
   - *Zero-portfolio consistency:* liquidation strategies never appear for a customer with no holdings.
   - *Non-degeneracy:* every grade 0–3 appears, no grade exceeds a configured share, and no single product, tenure or strategy wins a configured share of groups.

4. **The stress simulation is deliberately narrow and measured.** One parameterization — shock probability × magnitude × duration, fixed seed — and its contribution is quantified as a **label-flip rate** against a run with the simulation disabled. A flip rate below ~2% means it is doing nothing and should be removed; above ~30% means it has swamped the other signals. Either is a mis-parameterization to fix before training, and the measured rate is recorded in the dataset manifest.

5. **A human reads twenty of them.** Every dataset build writes `data/label_audit_sample.md`: twenty customers with their top and bottom candidates in plain language. Invariants catch logical flaws; only a person catches "these labels are self-consistent but no human would call that the best option." This is cheap and it is mandatory.

Blast radius is contained by `LABELING_POLICY_VERSION`, stamped into the dataset manifest and both model manifests, so a policy change forces a retrain and is visible in every decision trace.

### 17.2 The serving memory ceiling (Phases 0, 11, 13, 17)

**The risk.** Pandas + scikit-learn + the `shap` package + XGBoost + FastAPI loaded together approach or exceed the 512 MB of a free PaaS tier before a single model is loaded. Discovering this at deployment is fatal to a demo, because by then every module assumes DataFrames and every explainer calls `shap`.

**Resolution — the serving import graph is designed small from Phase 0, not trimmed at Phase 17:**

| Decision | Effect |
|---|---|
| Pandas is a **training-only** dependency; `app/ml/features.py` returns NumPy arrays and the catalogue loads into Pydantic models via the stdlib `csv` module | removes the single largest import |
| The isotonic calibrator is **exported as knots** and applied with `numpy.interp` | removes scikit-learn from serving entirely |
| Categorical encoding is a **saved dict mapping**, not a pickled `LabelEncoder` | removes the other scikit-learn dependency, and makes unseen categories a handled case instead of a crash |
| Feature contributions come from **XGBoost's native TreeSHAP**, not the `shap` package | removes `shap` (and its own heavy transitive deps) from serving |
| Models persist as **XGBoost JSON**, not pickle | smaller, version-robust, no joblib at serving |
| `requirements.txt` (serving) and `requirements-train.txt` (offline) are separate files | the deployment installs only what it runs |

Enforcement is a test, not a convention: after importing the application, `sys.modules` must contain none of `pandas`, `sklearn`, `shap`. **Memory is measured at Phase 11, Phase 13 and Phase 17** — a budget checked three times during the build, not a surprise at the end — via `scripts/measure_memory.py`, which reports resident memory after import, after model load, and after one `/recommend` call, against a ceiling in config. A single uvicorn worker is the default, because each worker loads its own copy of both models.

The mitigations above are expected to land serving well under the ceiling. If a target still cannot fit, the permitted lever is disabling the XAI endpoint by config flag. **Never** the fallback path, the grounding guards, the calibrator, or the primary recommender.

### 17.3 Grounding false positives (Phase 13)

**The risk.** A guard that rejects valid explanations gets switched off, and then nothing protects the user from an invented number. Indian numbering makes this acute: `6,00,000`, `6 lakh`, `6L`, `₹6L`, `0.6 million` and `600000` are the same figure, and `8%`/`0.08` and `48 months`/`4 years` are the same values in different clothes. Naive extraction plus strict matching produces a guard nobody trusts.

**Resolution — four decisions:**

1. **Prevention first: the payload carries display strings.** Every figure enters the prompt both as a number and as a pre-formatted string (`"₹6,00,000"`, `"48 months"`, `"8.0%"`), and the prompt instructs the model to reproduce them verbatim. The guard is then mostly comparing against strings the system itself wrote, which is a far easier problem than parsing arbitrary prose.

2. **Expand the accepted set rather than parsing every spelling.** From each payload figure, build a set of legitimate normalized representations at construction time — the value, its lakh/crore forms, its rounded forms at sensible precisions, percent/decimal duals, and month/year duals. Membership testing against a generously expanded set is robust in a way that open-ended parsing of the response is not.

3. **Three outcomes, not two.** This is the decision that actually solves false positives:

   ```
   GROUNDED     every extracted financial figure matched the payload      -> accept
   UNVERIFIED   a token could not be confidently parsed or classified     -> accept, flag, log
   UNGROUNDED   a token parsed confidently as a financial figure and has
                no match in the payload                                   -> reject, use template
   ```

   An unparseable token is a limitation of the guard, not evidence of a hallucination, and must not cost the user their explanation. `UNVERIFIED` responses are logged with the offending token so the normalizer improves from real traffic. Only a *confident* parse with no match rejects.

4. **A number is financial only in a financial context.** A token is treated as a financial figure when it is adjacent to a currency symbol, a percent sign, or a financial cue word (`EMI`, `interest`, `rate`, `tenure`, `months`, `years`, `score`, `lakh`, `crore`, `₹`, `Rs`), or when it exceeds a magnitude floor. Ordinals, list markers, "top 3", dates, and numbers inside words are excluded structurally. Requiring context — rather than only filtering by size — is what removes the bulk of false positives.

**The guard is locked in by a frozen corpus**, `tests/data/grounding_corpus.jsonl`, of labelled `GROUNDED` / `UNGROUNDED` / `UNVERIFIED` examples covering every Indian-numbering form above. The guard must reject **100%** of the `UNGROUNDED` cases — a missed invented figure is the failure that matters — and falsely reject **zero** of the `GROUNDED` cases. When a false positive appears in practice, the fix is a normalizer improvement plus a new corpus case. **Never a widened tolerance, and never a disabled guard.**

### 17.4 Why these are settled before Phase 0

All three are cheap now and expensive later. The labeling invariants cost nothing to write before the policy exists and are nearly impossible to retrofit onto a policy someone has already tuned. The serving import boundary is a one-line decision at Phase 0 and a rewrite of six modules at Phase 17. The grounding normalizer is a pure function with no dependency on any other component, so it can be validated against its corpus in isolation before the pipeline it protects exists at all.

`IMPLEMENTATION_PLAN.md` therefore opens with **Phase R**, a risk-reduction phase whose only outputs are validated parameters, invariant suites and a corpus — no production code.
